## Scope boundaries and documentation drift

- Real payment processing is not mandatory. `payments.refund` must remain explicitly simulated. Automated retraining is optional in Phase 9 and may remain deferred.
- Recurring schedules are implemented as manager-authored, bounded task submissions. They do not create an open-ended goal engine or event-triggered planner. Keep claims about standing goals limited to the actual behavior.
- Full mode has recurring schedules, which create normal guarded work. They do not imply persistent goals or event-triggered planning. Pilot mode excludes them; local regressions prove recurrence and pilot skip behavior, and the mounted browser confirmed a bounded create/pause/reopen/name-only-save flow. Resume/delete and the complete schedule lifecycle remain unverified in the browser.
- Pilot tasks now require passing required probation for the current spec/runtime/policy and a deployment matching the latest required run IDs. A policy change blocks pilot assignment/resume/execution/effects until fresh probation and deployment; see [`deployment-freshness.md`](deployment-freshness.md). This check is pilot-specific.
- Older test counts and release failures describe earlier commits. The latest isolated runtime release check at code `3131e20` reports 215 Node tests, Python 2/2, and 0 audit vulnerabilities under Node 22/Python 3.12. It is not a hosted CI result. The production doctor result at `51ecc6b` is historical; current configuration still needs validation.
- The earlier Solari `FeatureRequiresPlan` result came from a client requesting `stealth: true`; the current client sets `stealth: false`. Do not carry forward a paid-plan blocker without a new browser launch result. Provider-side browser egress control and sandbox video/replay evidence remain open.
